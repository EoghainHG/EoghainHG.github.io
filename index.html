  • Booted OpenSBI and a full, unmodified Linux kernel to a real interactive shell prompt on physical Kintex-7 hardware

Deep dive

Architecture & design decisions

A 5-stage IF/ID/EX/MEM/WB pipeline with separate instruction and data caches bridged to DDR3 over AXI4-Lite; MMIO ranges are decoded around the cache so peripheral accesses are never cached. Sv32 virtual memory lets the core run a stock Linux kernel unmodified. Peripherals (CLINT, PLIC, a 16550-compatible UART, an SPI master for SD, and a bit-banged I2C/GPIO block for the board's power monitors) sit behind an MMIO decoder. Programs load into DDR3 over JTAG before the CPU is released from reset, since the Genesys 2 has no hard processor system — the only path onto the board.

Verification approach

A Verilator regression suite covers the core, caches, MMU, interrupts, and every peripheral individually, plus the official riscv-tests ISA compliance suite and an OpenSBI boot test in simulation. Real hardware bring-up followed the same staged-risk discipline — each new subsystem (UART, DDR3 via MIG, SD) got its own isolated top-level bitstream before being folded into the full design, and a Basic-tier ILA was instantiated directly in RTL to capture real AXI/cache traffic on the board when a bug (intermittent instruction-fetch corruption) couldn't be root-caused from symptoms alone.

Results & what's next

MIG DDR3 calibration, the full AXI datapath, every instruction fetch in a real test program, and UART output are all independently confirmed correct on physical hardware, and Linux now boots to an interactive shell. Next: SD card storage over the board's native 4-bit SDIO pins, and video output.

Protocol Emulator — Jane Street Tiny Tapeout ASIC Entry

Sep. 2026 – Present
Verilog / SystemVerilogcocotb LibreLaneTiny TapeoutIHP CMOS5L

A reprogrammable, multi-protocol pin emulator built for a Jane Street-sponsored Tiny Tapeout ASIC competition. Four competing micro-architectures — a microcoded pin-sequencer, a tiny accumulator CPU, an FSM-plus-shift-register hybrid, and a distributed per-signal pattern-generator design — are benchmarked against a shared bar: implement SPI, UART, and I2C from loaded programs with the RTL frozen between them, confirmed not just in simulation but captured and decoded on real FPGA hardware.

  • Designed and benchmarked four candidate pin-sequencer architectures against a shared SPI-mode-0 baseline — 188 to 395 cells (0.8–1.6% of the ~24K-cell Tiny Tapeout budget) — versus a 6,202-cell (26%) reference design, reframing die area from a non-issue to a real constraint
  • Defined a pass bar that forces an honest comparison: all three required protocols (SPI, UART, I2C) must run from loaded programs with the RTL frozen between them — I2C's open-drain pins, clock stretching, and ACK turnaround are the discriminator none of the lean candidates handle yet
  • Caught a bug invisible to 109 passing simulation tests — the reference design's output pin never actually held its level on real hardware — by capturing and decoding each protocol on a Genesys 2 FPGA with a logic analyzer, and made that hardware-confirmation step mandatory for every candidate going forward
  • Measured that 10BASE-T Ethernet (Manchester-encoded, ~3.3 clocks per half-bit at Tiny Tapeout's 66 MHz pad ceiling) can't fit a programmable sequencer at any legal clock, and built it instead as dedicated hardware — a from-scratch serializer/deserializer/FCS datapath (596 cells) — validating the no-PHY, direct-pin-drive approach on real hardware via a hand-routed companion board before committing the pin budget on-chip

Deep dive

Architecture & design decisions

Four paradigms for the same job — sequencing pin actions from a loaded program — are built and compared head to head: a combinational microcode ROM driving pin actions and loop/branch fields directly; a tiny general-purpose accumulator core with a pin-oriented instruction set (protocol behavior lives entirely in firmware); dedicated shift-register and clock-divider primitives sequenced by a small explicit FSM; and independent per-signal countdown registers (SCLK, MOSI, MISO, CS_N, DONE) driven by one shared step pulse, with no central FSM state at all.

Verification approach

Per candidate: cells/µm² at full function, core clocks per bit per protocol, max bit rate at 50 MHz, program words per protocol, pins required, and — the discriminator the project treats as non-negotiable — whether it's been hardware-confirmed. Simulation agreement alone doesn't count: a prior design passed 109 simulation unit tests while its pin never held a real level on hardware, because every test happened to sample it in the one cycle it looked correct. Every candidate now has to be captured on a Genesys 2 FPGA and decoded against expected timing before it's recorded as passing.

Results & what's next

All four lean candidates clear SPI mode-0 at 188–395 cells; the riscy accumulator core also adds UART TX, at a cost (two new opcodes, a wider instruction word) that a prior analytical estimate missed entirely. I2C — open-drain, clock-stretching, ACK turnaround — is the next gate, since none of today's candidates handle it yet. Ethernet is explicitly out of scope for the programmable core (the clock-rate math rules it out) and lives instead as the separate fixed-function datapath described above.

Deep dive

Architecture & design decisions

Each core has its own CPU, I-cache, and D-cache with independent external memory ports. Both D-caches are write-through, so write-invalidate snooping is sufficient for coherence — every store from one core invalidates any matching line in the other core's D-cache. Hazards are handled with EX/MA→EX, MA/WB→EX, and MA/WB→RF forwarding, a 1-cycle load-use stall, and a 4-cycle mispredict penalty on resolved branches/JALR/traps (correctly predicted branches and all JALs cost nothing, since JAL is decoded in IF).

Verification approach

Verilator C++ testbenches run the official RV32UI/UM/UA ISA tests (generated as hex images, so no RISC-V toolchain is required) against both the single-core and dual-core tops, plus four hand-written multicore tests targeting cache coherence, a shared LR/SC counter, an LR/SC spinlock, and per-hart mhartid. The SRAM macro is swapped for a behavioral model in simulation, which synthesis also uses as a black box.

Results & what's next

Timing closes at every PVT corner (worst case +0.224 ns setup at max_ss_100C_1v60), with 66.3% instance utilization and 0 router DRC errors — but Magic/KLayout sign-off DRC and antenna repair are currently disabled to keep run time manageable, so this isn't tape-out clean yet: 707 nets still carry antenna violations and there are slew/cap violations at the slow and fast corners. Next: insert diodes during placement, give the floorplan more room, and re-run full sign-off DRC.

VLSI Standard-Cell Placement Engine

Jan. 2025 – May 2025
C++EigenPython EDA / Physical Design

A standard-cell placement flow for VLSI physical design, reading industry-standard Bookshelf-format benchmark circuits (the ISPD superblue12 benchmark) and implementing two independent placement strategies — min-cut recursive bipartitioning and quadratic (analytic) placement — sharing a common Fiduccia–Mattheyses partitioner.

  • Implemented the Fiduccia–Mattheyses (FM) min-cut partitioning algorithm from scratch in C++, with a bucket-list gain structure and checkpointing so FM results can be saved/reloaded instead of recomputed
  • Built a recursive bipartitioning placer that alternates horizontal/vertical cuts across the chip region, driven by FM partitioning at every level of recursion, with a legalization pass that removes overlaps while respecting fixed terminals
  • Built an independent quadratic placer that formulates placement as a sparse linear system (clique and star net models) solved via Eigen for minimum squared wirelength, followed by cell spreading and legalization
  • Built a Python visualization pipeline (scatter plot + density heatmap) to compare cell distribution and area utilization between the two strategies
→ github.com/EoghainHG/ESE556-project-2
Deep dive

Architecture & design decisions

FM min-cut partitioning is the shared primitive behind both strategies. The recursive bipartitioning placer repeatedly splits the chip's rectangular region in half, using FM to decide which cells belong in each half at every level, until each region holds a small group of cells. The quadratic placer instead builds a sparse connectivity matrix from the netlist and solves directly for cell positions minimizing squared wirelength, then spreads cells out to relieve density before legalizing.

Verification approach

Both flows were run against the ISPD superblue12 Bookshelf benchmark, parsing .nodes/.nets files and distinguishing movable cells from fixed terminals. Correctness was checked by rendering final placements as a scatter plot (fixed vs. non-fixed cells) and a density heatmap, confirming legalization eliminated overlaps and fixed terminals stayed in place.

Results & what's next

Both strategies converge to legalized, overlap-free layouts on superblue12, with the quadratic placer's density map noticeably tighter near the die edges than the min-cut placer's. Next step would be a wirelength-driven detailed placement pass on top of either global placer's output.

Architecture & design decisions

input_mems streams A then B into two single-port memories over AXI-Stream; TUSER carries K and a newA flag so A can be reused against a new B without re-streaming it. The top-level FSM steps through every (m, n) output pair, running K MAC cycles for each before handing the result to the output FIFO — default parameters are M=7, N=9, MAXK=8 with 12-bit signed inputs and 32-bit saturating outputs.

Verification approach

Physical verification runs the full LibreLane flow (Yosys → OpenROAD → Magic/KLayout → Netgen), with scripts/librelane_optimizer.py closing the loop automatically: it checks setup slack at the ss/100°C/1.60V corner, hold slack at the ff/−40°C/1.95V corner, and slew/cap/fanout violations, then patches the config and resumes from the right step — tracked run-over-run in librelane_run_history.json.

Results & what's next

The latest run (RUN_2026-05-05_21-24-17) closes at 21.79 ns with +12.19 ns / +3.35 ns setup slack (tt / ss) and 0 DRC/LVS errors, at 16.9 mW. A handful of slew, cap, and fanout violations remain at the typical corner, plus 33 antenna-violating nets — next step is running those through the same auto-tuning loop that closed timing.
